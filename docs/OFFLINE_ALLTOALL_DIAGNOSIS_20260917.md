# 离线 CABLE 为什么在 All-to-All 上退化

日期：2026-09-17。状态：诊断完成。复核原来的 960 次 All-to-All 运行，重建其中 384 次 CABLE／固定规则的全部初始选路；新增 900 次对照运行，2,260,800 条流全部完成。所有模型在传输期间冻结，没有在线训练。

## 结论

**直接瓶颈是初始路径分配造成的目的侧负载不均。原评分器在集中启动的 All-to-All 上，把过多完整流分配给少数 spine→目的 leaf 链路；这些链路需要处理的总数据量基本决定了最终完成时间。** 源 leaf 的出口总体均衡，并不代表每个目的 leaf 的入口也均衡。

评分器中远端队列、队列变化量和目的侧历史流量的组合，是已经通过干预确认的重要因素。只删除一个输入不一定改善：删除远端队列、保留其余项会严重恶化；同时移除远端排队、远端变化量和目的侧历史项，P95/P99 分别降低 **23.62%/26.41%**。这说明需要修正输入之间的配合，不能把结论写成“远端信息无用”。

单纯增加反馈频率或允许原模型重新选路都没有解决问题。离线训练本身并没有因此被否定；现有模型对这种流量的泛化不足，后续应优先改进初始分配和离线训练覆盖范围。

## 1. 退化集中在哪里

原始正式实验包括：32/64 个参与主机，1/8/64 KiB 每对端，两个拓扑，8 个流量种子，3 个冻结模型，以及 ECMP、weighted ECMP、DRILL、CONGA、LetFlow、适配 ConWeave 和同信息固定规则。

原 CABLE 对全部条件等权聚合后，P95/P99 相对 CONGA 增加 **23.01%/28.06%**，相对适配 ConWeave 增加 **18.93%/25.19%**。以下图使用全部原始条件，没有挑选个别模型或种子。

![原结果分解](../../../work/prisma_conweave_data/new_runs/offline-alltoall-diagnosis-20260917/figures/original_breakdown.png)

最明显的退化出现在 64 个参与主机时：对称拓扑下，相对固定规则的 P99 增加约 29.5–31.2%；非对称拓扑下增加约 22.6–24.0%。32 主机非对称场景中，CABLE 反而比固定规则快约 5–6%。所以不能概括成“所有 All-to-All 条件都一样差”，也不能只怪非对称链路。

物理网络始终是 128 主机、8 leaf、8 spine，每个 leaf 的总上联容量为 6 Gbps。参与者均匀分布到 8 个机架：32 主机时每机架 4 个参与者，64 主机时每机架 8 个。每台主机网卡为 1 Gbps；后者的发送峰值可达到每机架 8 Gbps，超过 6 Gbps 上联容量，因而更容易暴露路径分配不均的问题。这是容量与流量构造的解释，不是另一次独立的容量消融。

## 2. All-to-All 给原评分器带来了什么变化

这里测试的是 direct All-to-All：每个参与主机同时向其余全部参与主机发流。32/64 主机分别产生 992/4032 条传输，主机间仅有 0–5 μs 启动抖动。它没有 All-Reduce 的阶段依赖，也没有启动流量限速器。

“同时启动”不等于交换机同时看到所有首包：网卡仍按链路容量发送。在固定展示案例——种子 89001、模型 9101、64 主机、64 KiB、对称拓扑——跨机架流的初始路径选择发生在任务开始后 **9.5–553.4 μs**，而任务直到 **91.4 ms** 才完成。也就是说，决定后面几十毫秒负载分布的动作，几乎都在最初半毫秒内做完了。

原 CABLE 对每个新流根据当时观测重新评分，所以“参数冻结”并不等于“忽略实时状态”。问题在于：首包选路后整流固定，评分使用的是当前队列、收到的远端报告，以及已经经过本地交换机的历史数据量；它没有给已经选到这条路径、但后续数据尚未到来的完整流做负载预留。

在这个案例中，选中路径的反馈年龄中位数为约 **93.3 μs**。多个源 leaf 会看到相似的目的侧信息，各自分配新的流；报告中的当前队列不能完整表达这些源已经给未来作出的分配。这个过程与目的侧路径集中相符，但本文没有记录所有源之间的信息同步过程，不能声称已经单独量化了每一种同步效应。

## 3. 直接证据：出口均衡，目的侧却集中

从候选日志恢复 flow hash 的轮转顺序，结合流的源、目的、端口和链路速率，重建每条流的 spine 路径。这里的 spine 编号表示模拟器的稳定候选顺序，不冒充物理交换机数字 ID。所有重建运行都验证了原生评分和最终选择；非对称链路的速率映射也保持一致。

上述对称案例中：

- CABLE 最重源侧上联的分配量约为同类链路平均值的 **1.04 倍**，源侧看起来均衡。
- 最重目的侧链路却达到平均值的 **2.14 倍**；固定规则为 **1.68 倍**。
- 保持整流固定、只按本地队列选路，目的侧峰值降至 **1.43 倍**。
- 同时移除远端排队、远端变化量和目的侧历史项，目的侧峰值降至 **1.27 倍**。

这不只是一个案例的巧合。对原来全部 64 主机对称条件取平均，CABLE 的源侧峰值／平均值为 **1.023**，目的侧为 **2.091**；同信息固定规则分别为 **1.018** 和 **1.585**。

![目的侧路径分布](../../../work/prisma_conweave_data/new_runs/offline-alltoall-diagnosis-20260917/figures/destination_path_load.png)

图中按各路径容量应承担的数据量归一化。非对称图的理想分配让 1 Gbps 路径承担 500 Mbps 路径的两倍流量；不是要求所有链路分到相同字节数。

更直接的检查是计算分配完成后的不可避免服务时间：

```text
目的侧负载下界 = max_over_links(分配给该链路的有效载荷字节数 × 8 / 链路速率)
```

同一个对称案例：原 CABLE 的下界为 **83.89 ms**，实测任务完成时间 **91.40 ms**；本地队列对照的下界降到 **55.92 ms**，实测 **61.57 ms**。对应 P99 从 **91.04 ms** 降至 **60.99 ms**。

这说明不需要假设模型计算很慢，就能解释大部分时间：流已经被分到了这些链路上，即使链路一直满速发送，也必须花这么久。下界只计有效载荷，不计包头、控制报文、传播、发送间隙和拥塞控制，因此不能要求实测恰好等于下界。

![分配量与任务完成时间](../../../work/prisma_conweave_data/new_runs/offline-alltoall-diagnosis-20260917/figures/service_time_evidence.png)

384 次原始 CABLE／固定规则运行全部满足这个下界。任务完成时间／下界的中位数为 **1.118**，95 分位数为 **1.474**。这支持“分配后的链路工作量是关键瓶颈”，但不把跨消息大小的相关性当作额外的独立因果实验。

## 4. 哪些评分项导致了问题

原模型的有效评分是八个输入的线性组合，其中一个本地变化输入恒为零。远端时延既包含排队，也包含固定包长的链路发送时间，不能混为一个“队列项”。本次分别进行了精确拆分。

三个模型的远端时延／本地时延系数比约为 **0.92–1.63**，固定规则为 **0.25**。这不是“权重大就必然差”的证明，但说明原模型更容易受共同的目的侧信号支配。展示案例中，远端队列项的候选分数标准差约 0.107，本地队列项约 0.014；这是描述性分解，不把分数单位当作真实完成时间。

另外，9101/9102 两个模型给目的侧历史流量项学出了负权重：其他输入相同时，该路径近期发往这个目的机架的数据越多，分数反而越低，越容易继续被选中。9103 的该项为正，因此不能把全部退化只归因于这个负号。三个模型的远端变化量系数均为负，同样需要和当前队列项一起理解，不能孤立删项后就评价信息是否有价值。

### 控制变量结果

新实验采用原来的 2 个流量种子 89001/89002、全部 3 个冻结模型、32/64 主机、三档消息大小和两种拓扑。每种主要干预有 72 次配对运行；保持同一个流量、原模拟器、传输设置和其余模型参数。百分比是干预相对对应原 CABLE 的变化，负数表示更快。

![全部主要评分消融](../../../work/prisma_conweave_data/new_runs/offline-alltoall-diagnosis-20260917/figures/paired_interventions.png)

- **仅看本地队列：P95 −22.34%，P99 −21.95%。** 仍保持整流固定，并支付原有反馈开销。64 主机的对称／非对称 P99 分别降低 36.57%／37.14%；32 主机非对称则增加 4.29%，所以它不是已经验证的通用替代方案。
- **删除远端排队＋远端变化量＋目的侧历史项：P95 −23.62%，P99 −26.41%，任务完成时间 −26.29%。** 保留远端链路发送时间、本地队列和端口历史项。两个流量种子的聚合 P99 分别改善 26.63%／26.20%；三个模型分别改善 28.69%／26.15%／24.33%。
- **只删除目的侧历史项：P99 −3.76%。** 它确实是问题的一部分，但单独删除不能解释或修复全部损失。
- **删除远端排队＋变化量、保留目的侧历史项：P99 −2.04%。** 模型 9101/9102 分别恶化 14.85%／12.37%，9103 改善 27.15%。与上一个联合干预相比，说明这些项之间的相互作用很强。
- **只删除远端排队、保留变化量：P99 +73.12%。** 这是显著的负面结果。它说明随意去掉一个观测项，会破坏原评分中其他项的作用；不能据此说队列信息本身有害。
- **只删除远端变化量：P99 +2.04%。** 负权重也不能直接等同于错误参数。
- **只删除端口历史项：P99 +6.87%；同时删除两种历史项：+7.71%。** 端口历史在帮助分散流量，不能将所有历史输入一并视为问题。
- **删除显式链路发送时间项：P99 −3.09%。** 对称拓扑结果不变，因为这些项对所有路径贡献相同常数；改善主要来自 32 主机非对称场景。这是次要因素，不能解释对称 64 主机的严重退化。

“精确删除远端排队”是在导出的线性模型中把 `x1` 的权重贡献转移到 `x3`，再取消 `x1`：原来的 `x1 = remote_queue_delay + remote_serialization` 因而变成只保留 `remote_serialization`。不关闭反馈、不移除其网络开销，也不使用未来信息。另一个粗粒度对照直接删除完整远端时延及变化量，P99 改善 3.43%；它与精确删除排队不是同一个实验。

额外的零分数模型使用原有 flow hash 打破平局，并保留反馈报文。24 次运行相对 **9101 模型这一条谱系**的 P99 降低 16.54%；不能把这个数字写成对全部三个模型的比较，也不能把它当作原生 ECMP 的精确复现。

## 5. 为什么更快反馈、流中重选路没有直接解决

**反馈周期从 200 μs 缩到 20 μs：P95 +3.28%，P99 +3.39%。** 展示案例的选中反馈年龄中位数从 93.3 μs 降到约 10.2 μs，说明干预确实生效。它同时增加真实控制报文开销，并改变变化量输入；因此结论是“直接提高频率不足以修复原评分器”，不是“反馈年龄没有影响”。

**同一冻结模型允许 ACK 排空后重选路：P95 +5.88%，P99 +9.26%。** 决策至少间隔 50 μs，无在线学习；核验每次重选前所有已发字节已经累计确认。72 次运行发生 789,297 次重选决策、683,349 次实际路径变化，确实进行了重选，并非功能未触发。

由此，整流固定会让初始分配错误持续，但它不是必须先移除的根本约束：只改变初始评分、继续整流固定就能显著改善。直接让一个不适合该流量的评分器多做决策，反而可能更差。

## 6. 训练层面的解释：事实与尚未验证的假设

代码确认，原离线训练覆盖 uniform、storage、sweep、mixed，没有 direct All-to-All。All-to-All 集中启动、每源同时向多个目的发流、同一次任务的消息大小相同；这些结构与原训练分布不同。All-Reduce 则由真实完成事件逐步释放后续传输，新流选择分散到许多轮，不能据其正面结果推断 All-to-All 也应表现好。

原训练回报为：

```text
reward = -100 × [log(mean_FCT / 1 ms) + 0.25 × log(P99_FCT / 1 ms)]
```

它没有显式优化 P95、集合任务完成时间，或目的侧链路分配均衡。单个标量回报也不会自动保证在训练中没见过的通信结构上得到合适的系数组合。

因此，**训练分布不覆盖集合通信、奖励没有覆盖任务目标**，是有代码依据的设计缺口；但本次没有重新训练，也没有做奖励函数对照，不能把二者各自造成的损失量化，更不能声称换个 reward 就已解决问题。已验证的是现有冻结评分组合、路径分配和性能之间的关系。

## 7. 接下来合理的离线改进方向

优先沿着已定位的问题改，而不是恢复在线 RL：

1. 为初始分配提供“已经承诺给某路径的负载”信息，例如按目的机架统计的活跃流或本地预留量，避免仅依赖已经排出的数据和当前队列。无需使用真实未来流大小；估计值也必须单独做对照。
2. 检验近似同分路径的分散选择，减少多个源对共同报告作出过于一致的选择。现有 flow hash 只用于同分打破平局，不能打散所有近优路径。
3. 将 All-to-All、All-Reduce 的不同参与规模和消息大小加入离线训练／验证，在独立种子与未见过的条件上测试。加入任务完成时间目标，同时保留原流量下的 P95/P99 回归。
4. 用“同特征固定规则、同动作机制、学习与不学习”配对，证明重新训练的价值。当前删项结果仅是诊断，不直接作为新方法的最终成绩。

## 8. 核验、范围和复现

本次没有修改生产路由源码、原模型文件或论文。新增的是诊断运行器、分析／绘图脚本及本文。使用最初集合通信实验的冻结二进制和动态库，避免把后来的在线实现或 32 位流 ID 修复混入对比；这些集合任务最多 4032 条流，不触及旧 16 位 ID 上限。

612 次第一阶段运行包含 8 类主要干预各 72 次、24 次 hash 对照和 12 次原模型复跑。288 次第二阶段运行拆分远端排队与变化量。12 次复跑的 FCT、候选日志和诊断 JSON 与原实验逐字节相同。

每次运行核对配置、流量、拓扑、计划、模型和二进制哈希；从真实 start/finish 事件核验所有流大小和 FCT。重选路实验额外核验累计 ACK 边界。全部 900 次正常完成；统计按配对 log 比值等权聚合，不把不同运行的所有流混起来计算分位数。

这些消融复用了原测试集中的两个种子，且第二阶段根据第一阶段发现继续探索。它们是因果诊断和后续设计依据，**不是新策略的独立留出评测**；本报告不为两个种子的结果包装强泛化置信区间。原始退化分布图仍使用全部八个种子。
